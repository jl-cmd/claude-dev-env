Ignored is a filter, not a tab

The console on ci.example.internal has one list and a Filters rail. Four states sit in it: Escalated, Acted on, Untriaged, Ignored. I toggled Ignored on, watched the list change, then toggled it back off.

changes the plan

Untriaged is a third pile

An alert nobody opened is not a rejection. It is an alert nobody judged. Count Untriaged as ignored and every finding is poisoned. The counter holds it out.

confirmed

One call returns everything

Applying the Ignored filter fired no network request. The console filters data it already holds, pulled from /api/v1/alerts at a page size of 5,000. So the fetcher needs one pass, not four reads.

narrows your options

Cookies alone will not do it

I called /api/v1/alerts with session cookies and got 401 Unauthorized. The console sends a bearer header a plain client does not have. So a reader needs a signed-in session or its own token.

confirmed

The join key holds

Every alert links to /alerts/alert-1a2b3c?run=N. That is the alert_id plus run_index pair the existing export uses. New data joins onto the 2,480 rows on hand with no matching step.

still unknown

The field name for state

The console filters locally, so the triage state must ride in the /api/v1/alerts payload. I held no token to read a real response. That detail gets settled from a live payload while building.
